# **RU**

# **ТЗ кейса для HackAlem AI**

**Направление:** Аналитика и принятие решений / Кибербезопасность и комплаенс  
**Формат:** командная разработка, 5 часов  
**Данные:** предоставляются в начале хакатона, обезличенные

## **1\. Название**

**Граф денег: восстановление финансовой структуры организованной группы по транзакционной сети**

## **2\. Проблема**

Сейчас **AML-аналитик банка второго уровня** сталкивается с тем, что по итогам оперативной информации ему известен только **нижний уровень** преступной цепочки — конкретные клиенты, получавшие деньги, связанные с незаконным оборотом наркотиков. Кто стоит выше — кто собирает эти деньги, через кого их прогоняют и кто в итоге ими распоряжается — приходится восстанавливать вручную.

Из-за чего:

| Последствие | Масштаб |
| :---- | :---- |
| Ручная трассировка цепочки от одного клиента на 4 колена | часы работы аналитика на один узел |
| Основная часть сети остаётся невидимой | известен 81 клиент, реальная сеть — **2 248 узлов** |
| Блокируется только нижний уровень | организаторы сохраняют инфраструктуру и восстанавливают её за дни |
| Решения о приоритете проверки принимаются интуитивно | нет ранжирования, кого смотреть первым |

**Эффект от решения:** аналитик за минуты получает ранжированный список узлов с обоснованием роли каждого, вместо недель ручной трассировки; фокус проверки смещается с 81 «курьера» на реальные точки консолидации.

## **3\. Пользователь**

**Основной пользователь:** AML-аналитик / специалист подразделения финансового мониторинга банка второго уровня.

**Ключевой сценарий (от входа до результата):**

1. Аналитик получает от правоохранительных органов список клиентов, проходящих по делу (81 gid).

2. Загружает выгрузку исходящих переводов этих клиентов на 4 колена в инструмент команды.

3. Инструмент строит граф, считает метрики и **присваивает каждому узлу роль**: точка консолидации, транзит, распределитель, конечный получатель, периферия.

4. Аналитик видит схему сети с направлением потоков, подсветкой ролей и кластерами.

5. Аналитик открывает **топ-лист приоритетов**, читает обоснование по каждому узлу («получает от 11 разных плательщиков, отдаёт дальше 3% полученного») и формирует перечень клиентов на углублённую проверку и запрос в правоохранительные органы.

## **4\. Задача**

Разработать **аналитический инструмент (пайплайн \+ интерфейс просмотра)**, который по графу транзакций определяет роли участников финансовой сети и ранжирует их по значимости, и выдаёт аналитику готовую к работе модель структуры группы: участники, связи, направление денег, транзитные узлы, точки консолидации, кластеры, ключевые узлы.

Инструмент должен отвечать на вопрос аналитика: **«кого из этих 2 248 клиентов смотреть первым и почему»**.

## **5\. Вход → выход**

### **Вход**

| Параметр | Значение |
| :---- | :---- |
| Формат | 3 файла .parquet (edges, nodes, transactions) |
| Объём | 2 248 узлов, 3 119 рёбер, 4 840 транзакций |
| Период | 2026-07-01 — 2026-07-31 |
| Частота | разовая выгрузка (батч), онлайн-поток не требуется |
| Пример | предоставляется полный датасет, схема полей — в README.md датасета |

### **Выход**

Три CSV-выгрузки фиксированной схемы \+ экран просмотра.

**nodes\_roles.csv** — строка на каждый из 2 248 узлов:

| Колонка | Тип | Смысл |
| :---- | :---- | :---- |
| gid | int64 | идентификатор клиента |
| role | str | основная роль из словаря (см. ниже) |
| role\_score | float | уверенность в роли, 0–1 |
| cluster\_id | int | номер кластера |
| priority\_score | float | приоритет для аналитика, 0–1 |
| evidence | str | почему присвоена роль — до 200 символов, человекочитаемо |

**Словарь ролей** (обязательный минимум; команда может расширить, задокументировав):

| Роль | Смысл |
| :---- | :---- |
| consolidator | точка консолидации — аккумулирует средства от нескольких участников |
| transit | транзитный счёт — пропускает средства дальше, не удерживая |
| distributor | веерное распределение средств на много получателей |
| terminal | конечный получатель — деньги приходят и остаются |
| coordinator | координирующий узел, кандидат в организаторы |
| peripheral | периферия, признаков роли не выявлено |

**clusters.csv** — строка на кластер: cluster\_id, n\_nodes, n\_seed, sum\_kzt\_internal, top\_gids, hypothesis (гипотеза о назначении кластера).

**top\_nodes.csv** — ранжированный список **не менее 20** узлов: rank, gid, role, priority\_score, why (обоснование текстом).

**Экран просмотра:** схема сети с направлением потоков, подсветкой ролей/кластеров и поиском по gid. Веб-страница, ноутбук или desktop — на усмотрение команды.

**Допустимая задержка:** полный пересчёт от сырых .parquet до выгрузок — **не более 5 минут** на предоставленном объёме.

## **6\. Данные**

**Способ доступа:** архив с папкой data/ выдаётся всем командам в начале хакатона. Внешние источники не требуются и не предполагаются.

### **Состав**

| Файл | Строк | Содержание |
| :---- | :---- | :---- |
| edges.parquet | 3 119 | пара плательщик→получатель, агрегированная за период: src, dst, sum\_kzt, n\_tx, depth |
| nodes.parquet | 2 248 | уникальный клиент: gid, depth (минимальное колено), is\_seed |
| transactions.parquet | 4 840 | отдельная транзакция: src, dst, date, sum\_kzt |

Полное описание полей — в README.md датасета.

### **Как собран граф**

* стартовые вершины — 81 клиент, ранее выявленный как участник незаконного оборота наркотиков;

* прослеживаются **только исходящие** переводы, глубина обхода — **4 колена**;

* порог: транзакции **\< 5 000 KZT не попали в выгрузку**;

* только внутрибанковские переводы, июль 2026\.

Распределение по коленам: seed — 81, 1-е — 472, 2-е — 462, 3-е — 789, 4-е — 444\.  
Суммарный оборот в графе: **365 890 012 KZT**.

### **Качество и ограничения данных (объявлены заранее — их учёт оценивается)**

| Особенность | Что это значит для решения |
| :---- | :---- |
| **Обрыв на 4-м колене.** 444 узла имеют depth=4 и нулевые исходящие — это артефакт обхода, а не «деньги осели» | наивный признак «out\_degree \= 0 ⇒ конечный получатель» даст 444 ложных «сток» |
| **Только исходящие переводы.** Входящие потоки на узлы за пределами выборки не видны | нельзя достоверно считать полный баланс узла |
| **У seed-клиентов входящие суммы занижены** — граф собран *от* них, деньги, полученные ими извне выборки, в данные не попали | отношение «отдал / получил» у seed некорректно; 354 узла графа отдают больше, чем по данным получили |
| **Порог 5 000 KZT** | дробление ниже порога в данных невидимо |
| **19 из 81 seed отсутствуют в рёбрах**, ещё 12 присутствуют только как получатели | 31 seed не имеет исходящих переводов — учитывать при обходе |
| **16 слабосвязных компонент**: 1 877 узлов (46 seed), 270 (1 seed), остальные 14 — от 2 до 17 узлов | сеть не монолитна, 352 узла вне крупнейшей компоненты |
| **Нет атрибутов клиента** — ни ФИО, ни возраста, ни типа операции, ни остатков | только структура и суммы |
| **Нет размеченных ролей (ground truth)** | оценка — по обоснованности критериев, а не по accuracy |

**Лицензия и приватность:** данные обезличены (gid — синтетический идентификатор без привязки к личности), предоставляются исключительно для использования в рамках хакатона.

## **7\. Must have**

Без этих пяти пунктов решение не считается выполненным. К каждому — способ проверки.

| № | Обязательная функция | Как проверяется |
| :---- | :---- | :---- |
| **1** | **Воспроизводимый пайплайн.** Один запуск от сырых .parquet до всех трёх выгрузок, без ручных шагов | Жюри запускает команду из README на чистой машине; пайплайн отрабатывает \< 5 минут и создаёт 3 файла |
| **2** | **Роль и скор у каждого узла.** Все 2 248 узлов получили роль из словаря, role\_score и evidence | nodes\_roles.csv содержит 2 248 строк, все обязательные колонки заполнены, evidence непустой |
| **3** | **Критерии ролей задокументированы и объяснимы.** Для каждой роли — формальное правило или метрика с порогом | Жюри называет 3 произвольных gid; команда за минуту объясняет, почему роль именно такая, опираясь на свои метрики |
| **4** | **Кластеризация сети.** Узлы разбиты на группы, по каждому кластеру — размер, число seed, оборот и гипотеза | clusters.csv заполнен; cluster\_id есть у каждого узла в nodes\_roles.csv |
| **5** | **Топ-лист приоритетов \+ визуализация.** Ранжированный список ≥ 20 узлов с обоснованием и экран со схемой сети, где видно направление потоков и роли | top\_nodes.csv заполнен; на демо жюри называет gid — команда находит его на схеме и показывает его связи |

## **8\. Опционально**

Дают дополнительные баллы, сдачу не блокируют:

* **Учёт артефакта обрыва графа** — отделение настоящих конечных получателей от узлов, «обрезанных» 4-м коленом, с обоснованием метода.

* **Временные паттерны** — сквозной транзит (пришло и ушло в течение 1–2 дней), всплески активности, синхронные переводы от нескольких плательщиков в один день.

* **Поиск повторяющихся маршрутов и возвратных потоков** — устойчивые цепочки A→B→C и циклы, где деньги возвращаются к отправителю.

* **Детекция аномалий** — дробление сумм, аномальные профили узлов относительно их колена (правила или ML-модель).

* **Оценка устойчивости сети** — что произойдёт с сетью при изъятии топ-N узлов; распадается ли она на изолированные фрагменты.

* **AI-ассистент аналитика** — вопрос на естественном языке («кто собирает деньги с этих пятерых?») → ответ по графу со ссылками на узлы.

* **Автогенерация карточки узла** — краткая справка по клиенту: роль, потоки, связи, на что обратить внимание.

* **Оценка полноты** — указание, каких данных не хватает, чтобы закрыть белые пятна, и какой запрос аналитику стоит сделать следующим.

## **9\. Ограничения**

### **Нельзя**

* **Хардкодить результат** — зашитые в код списки gid под «правильный ответ» вместо расчёта.

* **Сдавать «чёрный ящик»** — роль без объяснимого правила или интерпретируемых признаков не засчитывается (см. must have 3).

* **Обогащать внешними источниками** и достраивать атрибуты клиентов, которых нет в данных (пол, возраст, доход, организация) — любые такие поля будут считаться выдумкой.

* **Требовать облачный кластер, GPU-обучение или платные сервисы** для воспроизведения результата.

### **Обязательно учесть**

| Требование | Что это значит |
| :---- | :---- |
| **Explainability** | каждая роль и каждая позиция в топ-листе сопровождается обоснованием, понятным аналитику без ML-образования |
| **Приватность** | данные обезличены; решение не должно предполагать работу с ФИО, ИИН или иными персональными данными |
| **Осторожность формулировок** | выводы формулируются как **гипотезы для проверки** («признаки консолидации»), а не как утверждение о виновности |
| **Производительность** | полный пересчёт ≤ 5 минут на предоставленном объёме, локально, на обычном ноутбуке |
| **Инфраструктура** | всё работает локально; интернет может потребоваться только для внешнего LLM API, если команда его использует |
| **Стек** | любой язык и библиотеки; рекомендуется Python (pandas, networkx/igraph) — стартовый код предоставляется |
| **Масштабируемость** | в README указать, что изменится в подходе при росте графа до \~1 млн узлов (текстом, реализация не требуется) |

# **KZ**

# **HackAlem AI үшін кейстің ТТ**

**Бағыты:** Аналитика және шешім қабылдау / Киберқауіпсіздік және комплаенс  
**Формат:** командалық әзірлеу, 5 сағат  
**Деректер:** хакатон басында беріледі, иесіздендірілген

## **1\. Атауы**

**Ақша графы: транзакциялық желі бойынша ұйымдасқан топтың қаржылық құрылымын қалпына келтіру**

## **2\. Мәселе**

Қазіргі уақытта **екінші деңгейдегі банктің AML-талдаушысы** жедел ақпарат қорытындысы бойынша оған қылмыстық тізбектің тек **төменгі деңгейі** ғана белгілі болатын жағдайға тап болады — есірткінің заңсыз айналымымен байланысты ақша алған нақты клиенттер. Жоғарыда кім тұрғанын — бұл ақшаны кім жинайтынын, оны кім арқылы айналдыратынын және ақыр соңында оған кім иелік ететінін — қолмен қалпына келтіруге тура келеді.

Себебі:

| Салдары | Ауқымы |
| :---- | :---- |
| Бір клиенттен 4 буынға дейін тізбекті қолмен трассировкалау | бір түйінге талдаушының бірнеше сағаттық жұмысы |
| Желінің негізгі бөлігі көрінбей қалады | 81 клиент белгілі, нақты желі — **2 248 түйін** |
| Тек төменгі деңгей ғана бұғатталады | ұйымдастырушылар инфрақұрылымды сақтап қалады және оны бірнеше күнде қалпына келтіреді |
| Тексерудің басымдығы туралы шешімдер интуитивті түрде қабылданады | кімді бірінші қарау керектігі бойынша рейтинг жоқ |

**Шешімнің әсері:** талдаушы апталар бойы қолмен трассировкалаудың орнына бірнеше минутта әр түйіннің рөлі негізделген түйіндердің рейтингтелген тізімін алады; тексерудің назары 81 «курьерден» нақты шоғырландыру нүктелеріне ауысады.

## **3\. Пайдаланушы**

**Негізгі пайдаланушы:** екінші деңгейдегі банктің AML-талдаушысы / қаржылық мониторинг бөлімшесінің маманы.

**Негізгі сценарий (кірістен нәтижеге дейін):**

1. Талдаушы құқық қорғау органдарынан іс бойынша өтетін клиенттердің тізімін алады (81 gid).

2. Осы клиенттердің 4 буынға дейінгі шығыс аударымдарының үзіндісін команданың құралына жүктейді.

3. Құрал граф құрады, метрикаларды есептейді және **әр түйінге рөл береді**: шоғырландыру нүктесі, транзит, таратушы, соңғы алушы, шеткері.

4. Талдаушы ағындардың бағыты, рөлдерді бөліп көрсету және кластерлері бар желі схемасын көреді.

5. Талдаушы **басымдықтардың топ-тізімін** ашады, әр түйін бойынша негіздемені оқиды («11 түрлі төлеушіден алады, алғанының 3%-ын әрі қарай береді») және тереңдетілген тексеруге және құқық қорғау органдарына сұрау салуға арналған клиенттер тізбесін қалыптастырады.

## **4\. Міндет**

Транзакциялар графы бойынша қаржылық желі қатысушыларының рөлдерін анықтайтын және оларды маңыздылығы бойынша рейтингтейтін, сондай-ақ талдаушыға топ құрылымының жұмысқа дайын моделін беретін **аналитикалық құрал (пайплайн \+ қарау интерфейсі)** әзірлеу: қатысушылар, байланыстар, ақшаның бағыты, транзиттік түйіндер, шоғырландыру нүктелері, кластерлер, негізгі түйіндер.

Құрал талдаушының мына сұрағына жауап беруі тиіс: **«осы 2 248 клиенттің қайсысын бірінші қарау керек және неліктен»**.

## **8\. Опционалды**

Қосымша ұпай береді, тапсыруға кедергі келтірмейді:

* **Граф үзілуінің артефактісін ескеру** — нақты соңғы алушыларды 4-ші буынмен «кесілген» түйіндерден әдісті негіздей отырып ажырату.

* **Уақыттық паттерндер** — өтпелі транзит (1–2 күн ішінде келіп, кетті), белсенділіктің күрт өсуі, бір күнде бірнеше төлеушіден синхронды аударымдар.

* **Қайталанатын маршруттар мен қайтарымды ағындарды іздеу** — A→B→C тұрақты тізбектері және ақша жіберушіге қайтып оралатын циклдер.

* **Аномалияларды анықтау** — сомаларды бөлшектеу, түйіндердің өз буынына қатысты аномальды профильдері (ережелер немесе ML-модель).

* **Желінің тұрақтылығын бағалау** — топ-N түйінді алып тастағанда желіге не болады; ол оқшауланған фрагменттерге ыдырай ма.

* **Талдаушының AI-ассистенті** — табиғи тілдегі сұрақ («осы бесеуінен ақшаны кім жинайды?») → түйіндерге сілтемелері бар граф бойынша жауап.

* **Түйін карточкасын автогенерациялау** — клиент бойынша қысқаша анықтама: рөлі, ағындары, байланыстары, неге назар аудару керек.

* **Толықтықты бағалау** — ақ дақтарды жабу үшін қандай деректер жетіспейтінін және талдаушыға келесі қандай сұрау жасаған жөн екенін көрсету.

## **Ұйымдастырушыларға арналған ескертпе**

Кейс деректерде тексерілген: жарияланған must-have 3–4 адамнан тұратын командамен 5 сағатта орындалады. Деректерде сөздіктің барлық рөлдеріне айқын үміткерлер бар — 8–24 түрлі төлеушіден кіріс аударымдары бар түйіндер, 60–116 алушыға желпуіш тәрізді жіберетін түйіндер, өткізу коэффициенті 0.8–1.2 болатын 72 түйін, ал базалық кластерлеу (Louvain) кезінде — бірден көп seed-клиентті қамтитын 8 тұрақты қауымдастық. Міндеттің шешімі бар, бірақ жалғыз дұрыс жауабы жоқ — бұл әдейі жасалған, бағалау критерийлердің негізділігі бойынша жүргізіледі.

# **Case Brief for HackAlem AI**

**Track:** Analytics and Decision-Making / Cybersecurity and Compliance  
**Format:** team development, 5 hours  
**Data:** provided at the start of the hackathon, anonymized

## **1\. Name**

**Money Graph: reconstructing the financial structure of an organized group from a transaction network**

## **2\. Problem**

Currently, **an AML analyst at a second-tier bank** faces a situation where, based on operational intelligence, only the **bottom level** of the criminal chain is known — specific customers who received money linked to illegal drug trafficking. Who stands above them — who collects this money, through whom it is moved, and who ultimately controls it — has to be reconstructed manually.

Because of this:

| Consequence | Scale |
| :---- | :---- |
| Manual tracing of the chain from one customer across 4 hops | hours of analyst work per node |
| Most of the network remains invisible | 81 customers are known, the actual network is **2,248 nodes** |
| Only the bottom level gets blocked | the organizers keep their infrastructure and rebuild it within days |
| Decisions on review priority are made intuitively | there is no ranking of whom to look at first |

**Impact of the solution:** instead of weeks of manual tracing, the analyst gets a ranked list of nodes with a rationale for each node's role within minutes; the focus of review shifts from 81 "couriers" to the real points of consolidation.

## **3\. User**

**Primary user:** an AML analyst / financial monitoring specialist at a second-tier bank.

**Key scenario (from input to result):**

1. The analyst receives from law enforcement a list of customers involved in the case (81 gids).

2. Uploads an export of these customers' outgoing transfers across 4 hops into the team's tool.

3. The tool builds a graph, computes metrics and **assigns a role to each node**: consolidation point, transit, distributor, final recipient, periphery.

4. The analyst sees a network map with flow directions, highlighted roles and clusters.

5. The analyst opens the **priority top list**, reads the rationale for each node ("receives from 11 different payers, passes on 3% of what it receives") and compiles a list of customers for in-depth review and a request to law enforcement.

## **4\. Task**

Develop an **analytical tool (pipeline \+ viewing interface)** that, based on the transaction graph, determines the roles of financial network participants, ranks them by significance, and gives the analyst a ready-to-use model of the group's structure: participants, links, money flow direction, transit nodes, consolidation points, clusters, key nodes.

The tool must answer the analyst's question: **"which of these 2,248 customers should I look at first, and why"**.

## **5\. Input → Output**

### **Input**

| Parameter | Value |
| :---- | :---- |
| Format | 3 .parquet files (edges, nodes, transactions) |
| Volume | 2,248 nodes, 3,119 edges, 4,840 transactions |
| Period | 2026-07-01 — 2026-07-31 |
| Frequency | one-off export (batch), no online stream required |
| Example | the full dataset is provided; the field schema is in the README.md of the dataset |

### **Output**

Three CSV exports with a fixed schema \+ a viewing screen.

**nodes\_roles.csv** — one row for each of the 2,248 nodes:

| Column | Type | Meaning |
| :---- | :---- | :---- |
| gid | int64 | customer identifier |
| role | str | primary role from the dictionary (see below) |
| role\_score | float | confidence in the role, 0–1 |
| cluster\_id | int | cluster number |
| priority\_score | float | priority for the analyst, 0–1 |
| evidence | str | why the role was assigned — up to 200 characters, human-readable |

**Role dictionary** (mandatory minimum; the team may extend it if documented):

| Role | Meaning |
| :---- | :---- |
| consolidator | consolidation point — accumulates funds from several participants |
| transit | transit account — passes funds on without holding them |
| distributor | fan-out distribution of funds to many recipients |
| terminal | final recipient — money comes in and stays |
| coordinator | coordinating node, candidate organizer |
| peripheral | periphery, no role indicators detected |

**clusters.csv** — one row per cluster: cluster\_id, n\_nodes, n\_seed, sum\_kzt\_internal, top\_gids, hypothesis (a hypothesis about the cluster's purpose).

**top\_nodes.csv** — a ranked list of **at least 20** nodes: rank, gid, role, priority\_score, why (text rationale).

**Viewing screen:** a network map with flow directions, highlighted roles/clusters and search by gid. A web page, notebook or desktop app — at the team's discretion.

**Acceptable latency:** a full recalculation from raw .parquet files to the exports must take **no more than 5 minutes** on the provided volume.

## **6\. Data**

**Access method:** an archive with a data/ folder is given to all teams at the start of the hackathon. External sources are neither required nor expected.

### **Contents**

| File | Rows | Contents |
| :---- | :---- | :---- |
| edges.parquet | 3 119 | payer→recipient pair aggregated over the period: src, dst, sum\_kzt, n\_tx, depth |
| nodes.parquet | 2 248 | unique customer: gid, depth (minimum hop), is\_seed |
| transactions.parquet | 4 840 | individual transaction: src, dst, date, sum\_kzt |

The full field description is in the dataset's README.md.

### **How the graph was built**

* starting vertices — 81 customers previously identified as participants in illegal drug trafficking;

* only **outgoing** transfers are traced, traversal depth — **4 hops**;

* threshold: **transactions \< 5,000 KZT were not included in the export**;

* intra-bank transfers only, July 2026\.

Distribution by hop: seed — 81, 1st — 472, 2nd — 462, 3rd — 789, 4th — 444\.  
Total turnover in the graph: **365,890,012 KZT**.

### **Data quality and limitations (announced in advance — accounting for them is evaluated)**

| Feature | What it means for the solution |
| :---- | :---- |
| **Cut-off at hop 4\.** 444 nodes have depth=4 and zero outgoing transfers — this is a traversal artifact, not "money settled" | the naive rule "out\_degree \= 0 ⇒ final recipient" produces 444 false "sinks" |
| **Outgoing transfers only.** Incoming flows to nodes from outside the sample are not visible | a node's full balance cannot be reliably calculated |
| **Incoming amounts for seed customers are understated** — the graph was built *from* them; money they received from outside the sample is not in the data | the "sent / received" ratio for seeds is incorrect; 354 nodes in the graph send more than they received according to the data |
| **5,000 KZT threshold** | structuring below the threshold is invisible in the data |
| **19 of the 81 seeds are missing from the edges**, another 12 appear only as recipients | 31 seeds have no outgoing transfers — take this into account during traversal |
| **16 weakly connected components**: 1,877 nodes (46 seeds), 270 (1 seed), the remaining 14 have 2 to 17 nodes | the network is not monolithic; 352 nodes are outside the largest component |
| **No customer attributes** — no name, age, transaction type or balances | structure and amounts only |
| **No labeled roles (ground truth)** | evaluation is based on how well-founded the criteria are, not on accuracy |

**License and privacy:** the data is anonymized (gid is a synthetic identifier not linked to any person) and is provided solely for use within the hackathon.

## **7\. Must have**

Without these five items the solution is not considered complete. Each comes with a verification method.

| № | Mandatory function | How it is verified |
| :---- | :---- | :---- |
| **1** | **Reproducible pipeline.** A single run from raw .parquet files to all three exports, with no manual steps | The jury runs the command from the README on a clean machine; the pipeline completes in \< 5 minutes and creates 3 files |
| **2** | **Role and score for every node.** All 2,248 nodes have a role from the dictionary, role\_score and evidence | nodes\_roles.csv contains 2,248 rows, all required columns are filled, evidence is non-empty |
| **3** | **Role criteria are documented and explainable.** For each role — a formal rule or a metric with a threshold | The jury names 3 arbitrary gids; within a minute the team explains why the role is what it is, based on its metrics |
| **4** | **Network clustering.** Nodes are split into groups; for each cluster — size, number of seeds, turnover and a hypothesis | clusters.csv is filled in; cluster\_id is present for every node in nodes\_roles.csv |
| **5** | **Priority top list \+ visualization.** A ranked list of ≥ 20 nodes with rationale and a screen with a network map showing flow directions and roles | top\_nodes.csv is filled in; during the demo the jury names a gid — the team finds it on the map and shows its links |

## **8\. Optional**

These give extra points but do not block submission:

* **Accounting for the graph cut-off artifact** — separating true final recipients from nodes "cut off" at hop 4, with a justified method.

* **Temporal patterns** — pass-through transit (in and out within 1–2 days), activity spikes, synchronized transfers from several payers on the same day.

* **Detecting recurring routes and return flows** — stable A→B→C chains and cycles where money returns to the sender.

* **Anomaly detection** — structuring of amounts, anomalous node profiles relative to their hop (rules or an ML model).

* **Network resilience assessment** — what happens to the network when the top-N nodes are removed; whether it breaks into isolated fragments.

* **AI assistant for the analyst** — a natural-language question ("who collects money from these five?") → an answer based on the graph with links to nodes.

* **Auto-generated node card** — a short summary of a customer: role, flows, links, what to pay attention to.

* **Completeness assessment** — indicating what data is missing to close the blind spots and what request the analyst should make next.

## **9\. Constraints**

### **Not allowed**

* **Hardcoding the result** — lists of gids built into the code for the "right answer" instead of calculation.

* **Submitting a "black box"** — a role without an explainable rule or interpretable features does not count (see must have 3).

* **Enriching with external sources** and adding customer attributes that are not in the data (gender, age, income, organization) — any such fields will be treated as fabricated.

* **Requiring a cloud cluster, GPU training or paid services** to reproduce the result.

### **Must take into account**

| Requirement | What it means |
| :---- | :---- |
| **Explainability** | each role and each position in the top list comes with a rationale that an analyst without ML training can understand |
| **Privacy** | the data is anonymized; the solution must not assume working with names, IINs or other personal data |
| **Careful wording** | findings are formulated as **hypotheses for verification** ("signs of consolidation"), not as statements of guilt |
| **Performance** | full recalculation ≤ 5 minutes on the provided volume, locally, on an ordinary laptop |
| **Infrastructure** | everything runs locally; internet access may be needed only for an external LLM API, if the team uses one |
| **Stack** | any language and libraries; Python (pandas, networkx/igraph) is recommended — starter code is provided |
| **Scalability** | the README should state what would change in the approach if the graph grew to \~1 million nodes (in text; no implementation required) |
